# Архитектор: зачем он нужен и что мы измерили

Материал для презентации и для судей. Сырые отчёты замеров лежат в
`backend/bench/results/2026-11-14-architect/report.md` и `…-architect-2/report.md`.
Замеры проверяющих агентов (без Архитектора) описаны в [review-benchmark.md](review-benchmark.md).

## Зачем он нужен (проблема, а не «ещё один агент»)

Задачи по историям пишут **параллельно и независимо**: на каждую историю свой генератор задач,
и друг друга они не видят. Для работы внутри одной истории это хорошо. Но у историй есть общие
вещи, и каждый генератор решает про них сам:

- кто вызывает внешний метод (например, создание отправления у курьера);
- где живёт клиент внешней системы, общая таблица, общий секрет;
- нужен ли сервису новый метод и кто его делает.

Что получалось на практике: два генератора независимо решали отдать один и тот же внешний вызов
разным сервисам, или оба писали один и тот же клиент. Итог: **внешний метод вызывается из двух
сервисов**, дубли задач, разошедшиеся контракты между сервисами.

Эти стыки потом ловят проверяющие (редактор стыков и скептик), но это дорого: лишний круг
доработки, время, вызовы модели. Дешевле решить общее **один раз до написания задач**.

Поэтому Архитектор — один агент между «историями» и «генераторами задач». Он не пишет задач.
Он выдаёт короткий план только про стыки:

- сервисы эпика и роль каждого;
- внешние вызовы: какой единственный сервис их делает, таймаут, безопасен ли повтор;
- связи между сервисами (через существующие методы контрактов, новый метод — только если нет);
- хранилища и общие секреты, их владелец;
- какая история делает каждую общую вещь (остальные только ссылаются);
- до 5 общих правил (дедлайны, повторы, журналирование, секреты).

Дальше план видят генераторы задач, рецензенты и скептик. Решения «с цитатой из источника»
обязательны. Решения без цитаты — «предположение Архитектора», его можно оспорить.

## Почему он не раздувает систему

- **Один вызов на эпик**, а не на каждую историю.
- **Цитаты проверяет код.** Остаются только цитаты, которые дословно найдены в источниках;
  выдуманное обоснование отсеивается.
- **План проверяется кодом** (`backend/app/architecture.py`): методы только из контрактов,
  у каждого внешнего вызова один сервис, у общей работы одна история. Если ошибки, один повтор.
- **Опора на существующую систему:** сервисы и методы берутся из документации, новые — только
  с объяснением. При малом числе источников план короткий.
- **Включён по умолчанию** (`ARCHITECT=true`), выключается `ARCHITECT=false`. Замер на четырёх эпиках
  (ниже) покажет, оставлять ли так; в бенчмарке остальные варианты явно идут без него.
- Промпт общий (`backend/prompts/architect.md`), без привязки к нашему демо: судьи загрузят свои эпики.

## Что измеряли

Полный прогон демо-эпика «Курьер-Экспресс» (Go, микросервисы) от эпика до задач.
Два варианта: `review` (как сейчас) и `review-architect` (то же + Архитектор).
Модель во всех замерах `deepseek-v4.1-flash` (через arcmux). Метрики считает код (`backend/bench/score.py`):

- **внешний метод в 2+ сервисах** — главный признак расхождения на стыках;
- **подтверждённых дублей** — дубли, которые подтвердил скептик;
- нерешённые находки, круги доработки, время, объём входа в модель.

### Замер 1 (3 прогона на вариант)

| показатель | review | review-architect |
|---|---|---|
| внешний метод в 2+ сервисах | 0,7 | 0,0 |
| подтверждённых дублей | 0,0 | 2,0 |
| кругов доработки | 1,7 | 1,3 |
| минут | 17,7 | 20,1 |
| вход, тыс. символов | 968 | 1057 |

### Замер 2 (5 прогонов на вариант, после правки промпта)

| показатель | review | review-architect |
|---|---|---|
| внешний метод в 2+ сервисах | 0,4 | 0,0 |
| подтверждённых дублей | 1,0 | 0,2 |
| нерешённых находок | 0,0 | 0,2 |
| кругов доработки | 1,4 | 1,6 |
| минут | 18,3 | 18,9 |
| вход, тыс. символов | 950 | 1264 (+33%) |

### Вместе (8 прогонов на вариант)

- Внешний метод в 2+ сервисах: **4 из 8 без Архитектора, 0 из 8 с ним.** Главная проблема
  на этом эпике исчезла.
- Время почти не изменилось (18–20 минут), вход в модель вырос на треть.
- Подтверждённые дубли шумят: в замере 1 с Архитектором их было больше, в замере 2 меньше.
  Вывод по дублям пока не делаем, нужен замер на большем числе эпиков.

## Какие проблемы Архитектора нашли и исправили

1. **Закрепляет спорное решение.** В планах `checkoutservice` почти всегда становился
   единственным клиентом курьера, хотя по документации подходил другой сервис. Исправлено:
   правило «опирайся на существующую систему» и обязательные цитаты.
2. **Первый план почти всегда не проходил проверку** (2 вызова Архитектора, +20–110 секунд).
   Теперь в событии `architecture_planned` пишется `first_problems`, чтобы видеть, как часто так.
3. **Общие секреты не распределялись по историям.** Исправлено: поле `story` у общей работы.

## Тесты кода

- `backend/tests/test_architecture.py`: проверка плана (методы, один сервис на вызов, цитаты,
  история общей работы), отсев выдуманных цитат, повтор при ошибках.
- `backend/tests/test_bench.py`: метрики бенчмарка (стыки, дубли, архитектура).
- Весь набор: `uv run pytest -q` → 112 passed.

## Что проверяем дальше

Всё выше проверено на **одном** эпике. Судьи загрузят свои, поэтому добавлены ещё три демо-эпика
с другими языками и стилями (`demo/shop-sbp-payments` Python/REST, `demo/clinic-sms-reminders`
C#/gRPC+REST, `demo/shop-currency-prices` Java/REST), у каждого в `demo.json` описаны внешние
контракты для проверки стыков.

Замер: 4 эпика × 2 варианта × 3 прогона = 24 прогона (~1,5 часа):

```
uv run python -m bench e2e --out bench/results/<папка> --repeats 3 --parallel 6 \
  --variants review,review-architect \
  --demos boutique-delivery,shop-sbp-payments,clinic-sms-reminders,shop-currency-prices
```

Правило решения: включаем Архитектора по умолчанию, если выигрыш на стыках держится на всех
четырёх эпиках и новых проблем нет, кроме времени и стоимости. Иначе остаётся экспериментом.
Результаты будут добавлены сюда.
