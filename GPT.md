2. ИСХОДНОЕ ЗАДАНИЕ НА ПРИЛОЖЕННЫХ СЛАЙДАХ

2.2. Проблема кейса «Агент-декомпозитор»

При использовании Scrum работа делится на Epic, пользовательские истории и технические задачи. Ручное разделение большого Epic на связанные истории и задачи затруднительно; требуется автоматизировать получение предварительного перечня.

2.3. Сценарий, непосредственно описанный в задании

1) Менеджер продукта вводит Epic проекта текстом.

2) При наличии загружает документацию разрабатываемого продукта.

3) Если Epic связан с интеграцией, загружает документацию другой системы.

4) При наличии API, например gRPC-контракта, загружает его.

5) При наличии добавляет примеры или реализованные контракты взаимодействия исходной системы.

6) Отправляет запрос в локальную LLM-систему из общей схемы.

7) После окончания отправки агент с помощью промпта формирует пользовательские истории и связанные задачи, выгружая результат в DOCX, XLSX и JSON.

8) При технической возможности автоматически добавляет истории и задачи в Jira, устанавливает взаимосвязи и назначает метку на основе имени Epic с суффиксом «\_Autogenerate».

9) В качестве дополнительного результата желательно выдать в JSON количество созданных историй и технических задач.

2.4. Дополнительные пожелания со слайда

— Определять либо запрашивать целевой язык программирования по документации проекта или API.

— Предусмотреть интеграцию с Jira.

— Хранить полученные результаты генерации.

— Сравнивать сгенерированный результат с итоговым перечнем задач и выдавать рекомендации по отладке промпта или формированию запроса.

— Основной промпт вынести в отдельный файл с возможностью настройки и отладки в будущем; для дополнительных промптов это также желательно.

Это требования и пожелания источника. Отдельные предложенные ниже механизмы — например, обязательное подтверждение публикации человеком — добавлены ChatGPT при проектировании, а не дословно взяты со слайда.

4. ПЕРВОНАЧАЛЬНАЯ ПРОДУКТОВАЯ КОНЦЕПЦИЯ

Рабочее название: AI Epic Decomposer.

Целевая аудитория: Product Manager, аналитик, Tech Lead.

Основной маршрут:

Epic + документация + API-контракты + примеры интеграций → анализ контекста → выделение требований → User Stories → Technical Tasks → проверка → ручное редактирование → экспорт.

Продукт должен быть не оболочкой над большим промптом, а системой, в которой LLM предлагает структуру, а приложение контролирует корректность данных, связи и пригодность результата к использованию.

Из исходного кейса ChatGPT выделяет локальную LLM, несколько видов контекста, иерархию задач, канонический JSON, экспорт DOCX/XLSX, необязательную Jira и контроль качества генераций/промптов.

5. ПРЕДЛОЖЕННЫЙ ВЕБ-ИНТЕРФЕЙС: ТРИ ОСНОВНЫХ ЭКРАНА

5.1. Создание и настройка Epic

Поля и действия:

— название Epic;

— текст требований;

— загрузка контекста проекта;

— при необходимости язык программирования, детализация и другие параметры;

— запуск декомпозиции.

Начальные форматы источников: обычный текст, Markdown, DOCX, JSON/YAML с OpenAPI, текстовые .proto-контракты. PDF предложено отложить до стабилизации основного сценария.

До генерации интерфейс должен показывать, какие документы прочитаны, какие API найдены и какие файлы обработать не удалось.

5.2. AI Workspace

Двух- или трёхпанельный рабочий интерфейс:

— слева дерево Epic → Stories → Tasks;

— в центре выбранная история или задача;

— справа источники требований и результаты проверки.

Пользователь редактирует формулировки, удаляет лишние задачи, добавляет свои и повторно проверяет результат. Новая генерация не должна уничтожать ручные правки предыдущей версии.

Сущности должны быть структурированными и редактируемыми, а не единой простынёй Markdown.

5.3. Проверка и публикация

Экран итогового отчёта:

— покрытие требований;

— корректность структуры и родительских связей;

— наличие критериев приёмки;

— нерешённые вопросы;

— экспорт JSON/DOCX/XLSX;

— при готовой интеграции — Jira.

Покрытие предложено считать по связям требований с историями, а не по субъективной оценке LLM.

Публикацию в Jira ChatGPT предлагает выполнять только после подтверждения человеком, без автоматической массовой записи непроверенных задач.

5.4. Статус примеров в интерфейсе

Epic о возврате платежей, файлы product-spec.docx/payments-api.yaml, POST /refunds, показатели «5 историй, 17 задач, 2 вопроса» и покрытие «12/14» — вымышленные иллюстрации будущего интерфейса. Это не данные реального проекта и не результаты уже работающего MVP.

6. BACKEND И ИНФРАСТРУКТУРНАЯ СХЕМА

Предлагается модульный backend в одном проекте плюс отдельный процесс генерации. Микросервисы для 40-часового MVP не нужны.

Компоненты:

— Web Application: ввод, просмотр, редактирование.

— Backend API: проекты, документы, генерации, экспорт.

— Generation Worker / Orchestrator: длительная обработка, parser/planner/validator.

— LLM Gateway: существующий HAProxy → vLLM / Qwen.

— Storage: Epic, исходные файлы, задачи, версии.

— Integrations: Bitbucket, Jira, экспорт.

Хранилище и интеграции вызываются backend и worker, а не самой LLM.

Модули backend:

1) Project / Epic Service — проекты, Epic, настройки.

2) Document Ingestion — загрузка, извлечение, нормализация документов.

3) Context Builder — сбор релевантного контекста.

4) Generation Orchestrator — управление этапами генерации.

5) LLM Client — обращение к локальной модели через шлюз.

6) Validation Engine — схемы, требования, связи, ошибки.

7) Plan Service — редактирование и версионирование плана.

8) Export Service — JSON, DOCX, XLSX.

9) Jira Adapter — подключение и создание задач.

Фоновый worker нужен, чтобы долгие обращения к модели не блокировали HTTP-запросы.

Bitbucket предлагается не переписывать: webhook уже присутствует на схеме. В продукте возможны ручной запуск и запуск/обновление контекста по событию репозитория. Для MVP основной путь — ручной; webhook можно использовать для обновления документов или отметки устаревшего контекста. В ответе упомянуты repo:push и проверка подписи webhook.

7. БИЗНЕС-ЛОГИКА: ШЕСТЬ ЭТАПОВ PIPELINE

7.1. Извлечение контекста

Backend разбирает Epic, документы, контракты и ограничения:

— OpenAPI превращает в список операций;

— .proto — в сервисы, RPC и сообщения;

— обычные документы — в текстовые разделы.

Каждому фрагменту присваивается ID источника для последующего объяснения происхождения задач.

7.2. Выделение требований

LLM выделяет атомарные функциональные, интеграционные и нефункциональные требования. Требования получают ID вида REQ-001.

Иллюстрации из ответа: проверка допустимости возврата, запрос провайдеру, предотвращение двойного списания.

7.3. Генерация User Stories

Для логического пользовательского сценария создаются:

— история;

— пользовательская ценность;

— критерии приёмки;

— связи с требованиями.

Story должна описывать результат для пользователя, а не техническую операцию вроде создания контроллера.

7.4. Техническая декомпозиция

Формируются задачи по backend, frontend, интеграциям, БД, тестам и обработке ошибок — там, где это действительно требуется.

У задачи должны быть описание, ожидаемый результат, критерии готовности, родительская Story и ссылки на документы.

7.5. Автоматическая валидация

Проверяются:

— JSON Schema и обязательные поля;

— родительские и прочие связи;

— дубли;

— критерии приёмки;

— покрытие требований;

— существование указанных источников.

Неоднозначности выводятся отдельными вопросами. Модель не должна компенсировать отсутствие информации выдуманными API.

7.6. Human Review

Пользователь проверяет, исправляет, утверждает версию и экспортирует план. После ручных правок должна быть возможна повторная проверка без полной повторной генерации Epic.

7.7. Роли агентов

Логические роли: Requirements Analyst, Technical Architect, Quality Reviewer.

Физически предлагается один оркестратор, несколько специализированных промптов и строгие схемы входа/выхода, а не сложная сеть самостоятельно общающихся агентов. Если LangGraph уже есть, этапы можно оформить его узлами.

JSON Schema на стороне vLLM рассматривается как помощь в получении структурированного ответа, но не как замена серверной валидации.

8. МОДЕЛЬ ДАННЫХ, ВЕРСИИ, СОСТОЯНИЯ И API

8.1. Канонический формат

Основной результат хранится как структурированный JSON. Из него строятся UI, проверки, экспорт и интеграции.

В примере JSON присутствуют:

— epic: id, title;

— requirements: id, text, source_refs;

— stories: id, title, description, acceptance_criteria, requirement_ids;

— вложенные tasks: id, title, description, definition_of_done, source_refs;

— open_questions.

Пример связывает REQ-001 с US-001 и TASK-001, указывает источник epic:section-1 и контракт payments-api:post-refunds. Это пример структуры, не окончательная утверждённая схема API.

8.2. Основные сущности

Project, Epic, SourceDocument, Requirement, GenerationRun, PlanVersion, UserStory, TechnicalTask, PromptVersion, ExportArtifact, JiraMapping.

Для MVP не предлагается отдельная таблица под каждый тип: допустимо хранить целый структурированный план в JSON-поле версии, а отдельно — метаданные Epic, файлов, запусков и интеграций.

8.3. Состояния

queued → processing → needs_review → approved.

Отдельно: failed.

Экспорт и публикация — операции над утверждённой версией.

Для каждого запуска сохраняются входной контекст, версия промпта и результат.

8.4. Предложенный минимальный HTTP API

POST  /epics                         — создать Epic.

POST  /epics/{id}/sources            — загрузить документы.

POST  /epics/{id}/generate           — запустить декомпозицию.

GET   /jobs/{id}                    — узнать статус генерации.

GET   /epics/{id}/plan               — получить актуальный план.

PATCH /plans/{id}                   — сохранить правки.

POST  /plans/{id}/validate           — проверить результат.

POST  /plans/{id}/export             — получить выбранный формат.

POST  /plans/{id}/publish/jira       — опубликовать после подтверждения.

Frontend для MVP может опрашивать статус задания. WebSocket для прогресса — последующее улучшение, а не необходимый стартовый компонент.

9. ОТЛИЧИТЕЛЬНЫЕ ВОЗМОЖНОСТИ ПЕРВОНАЧАЛЬНОГО MVP

9.1. Explainable AI Decomposition / Traceability View

У задачи видно, почему она появилась и каким требованиям/контрактам соответствует.

Пример: требование исключить повторный возврат → история безопасного возврата → задача проверки статуса + задача защиты от повторной обработки. Если контракт не описывает идемпотентность, система формирует открытый вопрос, а не скрывает отсутствие данных.

Для базовой визуализации не требуется отдельный графовый движок: связи уже находятся в JSON.

9.2. Impact Analysis

После изменения требования подсвечиваются связанные истории и задачи. В пределах хакатона достаточно определить затронутые элементы и предложить их пересмотр, не выполняя полную автоматическую регенерацию.

10. ПРИОРИТЕТЫ И JIRA ДО СРАВНЕНИЯ С OPENSPEC

Первоначальный P0:

— Epic из текста;

— документы и контракты;

— локальная LLM;

— генерация Stories/Tasks;

— структурированный JSON;

— просмотр и редактирование;

— базовая валидация;

— экспорт JSON/DOCX/XLSX;

— минимальное сохранение результата и версий.

Первоначальный P1:

— ссылки на исходные требования как основная wow-функция;

— Jira при готовом доступе.

Первоначальный P2:

— Impact Analysis;

— UI отладки промптов;

— полный анализ Git-репозитория;

— автоматическое самоулучшение промптов.

При интеграции Jira нужно учитывать конфигурацию конкретного проекта: технические работы могут быть Subtask под Story либо отдельными Task со связями. В ответе отмечаются зависимость обязательных полей от проекта и Atlassian Document Format для описаний REST API v3.

Минимальная Jira-интеграция: выбор проекта, предварительный просмотр, отправка подтверждённых элементов, сохранение полученных Jira ID. Повторная публикация не должна создавать дубликаты.

11. ПЛАН РЕАЛИЗАЦИИ НА 40 ЧАСОВ

0–4 часа — фундамент:

Зафиксировать JSON, подготовить тестовый Epic, проверить модель, создать каркасы frontend/backend.

4–12 часов — первый сквозной сценарий:

Ввод Epic → загрузка документов → LLM → сохранение структурированного результата.

12–22 часа — полная декомпозиция:

Requirements → Stories → Tasks, экран результата, редактирование, проверки связей.

22–30 часов — экспорт и качество:

JSON/DOCX/XLSX, история генераций, покрытие требований, источники основных задач.

30–35 часов — отличительная функция:

Traceability View, визуальные улучшения, Jira при готовом подключении; стабильный pipeline не ломать ради дополнительных функций.

35–40 часов — стабилизация и демо:

Прогоны, проверка экспорта, ошибки, резервный локальный пример, репетиция защиты.

Предлагаемое разделение команды:

14. ТРИ КЛЮЧЕВЫЕ ФУНКЦИИ ОБНОВЛЁННОЙ КОНЦЕПЦИИ

14.1. Evidence-based decomposition

Каждая задача имеет обоснование: требование Epic и конкретные фрагменты документов/контрактов. Источник можно открыть. Задача, выведенная из предположения модели, явно требует подтверждения.

Пример в ответе: TASK-014 опирается на REQ-008, payments-api.yaml и [integration-guide.md](http://integration-guide.md).

14.2. AI Gap &amp; Conflict Detection

Система находит не только задачи, но и недостающие данные.

Демонстрационный пример:

Epic требует повторной отправки платежа, а контракт не описывает идемпотентность. Выводятся технический пробел, риск повторного списания и рекомендация уточнить контракт/согласовать стратегию. Требуется решение Tech Lead.

14.3. Requirements Coverage &amp; Impact Analysis

Связь: Requirement → User Story → Technical Task → API Contract.

Вопросы, на которые должна отвечать система:

— какие требования не покрыты;

— какие задачи не имеют обоснования;

— какие требования покрыты частично;

— что затронет изменение требования;

— какие контракты не учтены.

Визуально это предлагается показывать графом или матрицей связей.

Обновлённый P0: загрузка Epic/документов, извлечение требований, OpenAPI, генерация Stories/Tasks, привязка к источникам, Gap Detection, Coverage Matrix, редактирование, три формата экспорта.

Обновлённый P1: Jira, Impact Analysis.

Обновлённый P2: полноценный Design Document.

Существенное изменение: источники и покрытие поднимаются в обязательное ядро, а Impact Analysis — из P2 в P1.

Для защиты предлагается Epic и два документа с заранее заложенным пробелом или противоречием. Главная демонстрация — найденная проблема, её источник и вопрос Tech Lead, а не просто 20 сгенерированных задач.

25. ИТОГ В ОДНОМ АБЗАЦЕ

Ветка начинается с проектирования 40-часового MVP, который на локальной LLM преобразует Epic и техническую документацию в редактируемые Stories/Tasks с JSON, проверками и экспортом DOCX/XLSX. После сравнения с OpenSpec акцент предлагается перенести с простой генерации backlog на доказательную декомпозицию, поиск пробелов и противоречий, покрытие требований и прослеживаемость до API/документов. Обсуждение инфраструктуры проходит от серверной Qwen3.8-27B к локальной Qwen3.5-9B, затем, по прямому пожеланию пользователя избежать тяжёлых моделей, к первому тесту Bonsai 2 9B PQ2_0 с облегчённым вариантом 4B. Ни стек, ни финальная модель, ни реальная работоспособность на ноутбуке в этой ветке ещё не подтверждены.
