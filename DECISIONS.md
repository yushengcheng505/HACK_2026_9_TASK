## 2. Принятые решения

### Модель и инфраструктура
- **Модель подключается по API**: любой OpenAI-совместимый endpoint (llama-server, vLLM,
  при желании облачный API для сравнения). Провайдер, адрес и модель — в конфиге, код не меняется.
- Локальная модель работает **на ноутбуке HONOR** (на нём же демо):
  `prism-ml/Ternary-Bonsai-2-9B` через `llama-server` (форк llama.cpp от PrismML; Ollama не подходит).
  Сразу замеряем скорость через `llama-bench`: только CPU и Vulkan (Intel Arc).
  Машина с NixOS и AMD R7 — только для разработки кода, модель на ней не держим.
- Демо: аренда GPU на clore.ai, **vLLM + `Qwen/Qwen3.8-27B-FP8`** на карте с 48 ГБ
  (L40S или A6000, примерно $0.4–0.5/ч).
  Запасной вариант: llama.cpp + GGUF Q4_K_M на RTX 4090/5090.
- HAProxy есть на схеме, поэтому используем его по-настоящему:
  - основной сервер — vLLM на clore;
  - резервный — `llama-server` с Bonsai на ноутбуке.
- Режим thinking:
  - на шаге планирования — на минимуме, поток рассуждений показываем в UI;
  - на шагах генерации JSON — выключен.
- Развёртывание: `docker compose up` на ноутбуке (backend, frontend, HAProxy, резервный llama-server).
  vLLM — на clore.ai. Вебхук Bitbucket доходит через туннель cloudflared.
- Интернет на площадке может подвести, поэтому есть режим проигрывания записанного прогона.

### Бэкенд — всё на Python
- Python 3.12 (uv), FastAPI, **LangGraph внутри процесса**, `SqliteSaver` (состояние графа,
  паузы на вопросы), SQLite (запуски, результаты, версии промптов).
- События на фронт идут по SSE, формат событий наш.
- Тот же модуль графа открывается через `langgraph dev` в LangGraph Studio. Это инструмент
  разработчика, а не часть демо. Studio нужны интернет и аккаунт LangSmith, но трассировка
  в LangSmith **выключена**, потому что данные не должны уходить наружу.
- Прослойка LLM: только OpenAI-совместимый API. Адрес и модель задаются в конфиге.
  Каждый ответ проверяется через Pydantic. При невалидном ответе — повтор с текстом ошибки.
  Где сервер умеет, используем `response_format: json_schema`.
- Промпты лежат в файлах `prompts/*.md` в git. Версии промптов хранятся в SQLite.
- Документы: `python-docx`. Таблицы: `openpyxl`.

### Граф агента
Генерация разбита на маленькие шаги, по одному узлу графа на шаг. Принцип: **LLM отвечает
за смысл, всё детерминированное делает код** (разбор контрактов, проверки, покрытие, выгрузка).
Загруженные документы — данные, а не инструкции: их текст не меняет правила генерации.

1. **Разбор входов (код).** OpenAPI → список операций, `.proto` → сервисы, RPC, сообщения,
   документы (md/txt/docx, **без PDF**) → разделы. У каждого фрагмента ID (`DOC-3`,
   `API:POST /orders`, `PROTO:Telemetry.GetSnapshot`). Если фрагментов слишком много,
   отбираем их через BM25. Векторной базы нет.
2. **Определение целевого языка программирования:**
   - сначала эвристика: расширения файлов в репозитории, опции в `.proto`, подсказки в OpenAPI;
   - затем подтверждение моделью;
   - при низкой уверенности — вопрос пользователю.
3. **Выделение требований (LLM).** Атомарные требования `REQ-001…`: функциональные,
   интеграционные, нефункциональные. У каждого ссылки на источники.
4. **Аналитик (LLM).** Ищет неясности и задаёт 3–5 вопросов с 2–3 вариантами ответа и полем
   «свой ответ». Граф встаёт на паузу.
   - «Пропустить» — агент принимает допущения и явно записывает их.
   - Запуск по вебхуку — идём сразу по допущениям.
   - **Уровень 2, «по возможности»:** здесь же поиск пробелов и противоречий между эпиком,
     документацией и контрактом. Пример: эпик требует повтора платежа, а контракт не описывает
     идемпотентность → пробел, риск, вопрос к техлиду. В 3D это красный узел с лучами
     к двум источникам. В демо-контенте заранее закладываем 1–2 противоречия.
5. **Истории (LLM)**, каждая ссылается на `REQ-xxx`.
6. **Задачи (LLM)** отдельно для каждой истории. Каждая ссылается на `REQ-xxx` и фрагменты
   контракта. Включая задачи на интеграционное тестирование с тест-сценариями
   (уровень 2): метод, входные данные, ожидаемый результат, ошибки.
7. **Проверки кодом («ОТК»).**
   - Схема и обязательные поля, связи с родителями, дубли.
   - **Существование каждой ссылки**: ссылка на несуществующий RPC — выдуманный API, брак.
   - **Покрытие по связям**: требования без историй, задачи без обоснования, задействованные
     методы контракта без задач. Методы, которые не использует ни одно требование, —
     отдельный список «не задействовано — подтвердите» (это не ошибка).
8. **Критики-LLM только по смыслу**: INVEST, формат «Как… я хочу… чтобы…», критерии приёмки,
   соответствие языку и стеку. Получают и замечания от проверок кода. Не больше 2 кругов.
9. **Выгрузка** DOCX / XLSX / JSON, включая статистику (п. 9).
10. **Jira**: REST API v3 (описание в формате ADF), Epic → Story → **Sub-task**
    (Task в Jira нельзя сделать дочерним к Story). Метка `<EpicSlug>_Autogenerate`.
    - Из UI: просмотр → кнопка «Опубликовать». По вебхуку: автоматически, как в задании.
    - Сохраняем ID созданных задач: повторная публикация обновляет, а не дублирует.
    - Трекер подключается через адаптер.

После ручных правок в UI запускаются только проверки кодом (п. 7), без новой генерации.

Одна модель на все шаги, разные промпты.

### Интеграции
- Jira Cloud Free для демо.
- Bitbucket Cloud. Сценарий: push в `epics/*.md` → вебхук с проверкой подписи HMAC →
  агент читает `docs/` и `contracts/` из репозитория → результат уходит в Jira и в UI.
  Ручной запуск из UI остаётся основным.
- Уровень 3, без фокуса: вопросы комментарием в Bitbucket, коммит файлов результата обратно,
  анализ последствий (изменённый `.proto` в push → какие задачи затронуты).

### Лаборатория (сравнение с итоговым списком)
- Главный режим — **валидация декомпозиции аналитика**: представитель прямо сказал, что ИИ нужен
  «для валидации этой работы и её ускорения». Второй режим — отладка промпта.
- Итоговый список загружается в нашем же формате `.xlsx`: выгрузили → люди поправили → загрузили.
- Сопоставление задач делает LLM-судья через строгий JSON. На выходе: совпадения, лишнее,
  пропущенное, процент покрытия, рекомендации к промпту и к запросу.
- Это и внутренний инструмент проверки качества: прогоняем на 3–5 эталонных эпиках после
  каждой правки промпта.

### Фронтенд
- React + Vite + react-three-fiber + drei + postprocessing + Tailwind.
- Стиль — «инженерный чертёж»: синяя сетка, тонкие линии, свечение, моноширинный шрифт,
  фирменный синий Элары. Панели метрик в стиле центра управления полётами.
- Обязательные экраны: 3D-сцена, табличный вид с редактированием, экран вопросов, экран лаборатории.
- В первый час фиксируем контракт событий с фронтом (`node_started`, `story_created`,
  `task_created`, `critic_rejected`, `question_asked`, `token`, `run_finished`, …) и файл
  с записанным прогоном. Этот же файл — запасной вариант на демо. Если понадобится, формат дорабатываем.

### Контент — первые 2 часа, генерируем с помощью ИИ
- Два набора эпиков:
  - (а) обычные веб-эпики;
  - (б) эпики из мира Элары: **интеграционные** (SCADA, телеметрия, gRPC, Qt-клиент, C++/C#).
- Для каждого эпика: документация, `.proto`/OpenAPI, эталонная разбивка.
- Всё на русском, в классическом формате User Story с критериями приёмки.

### Питч
- Главная фраза: **«Не генератор задач, а проверка полноты интеграции: каждая задача обоснована
  источником, каждый пробел найден до того, как его найдёт заказчик»**. Название продукта — позже.
- Главное: «понимает ваши контракты и код, каждая задача обоснована ссылкой на источник».
- Фундамент: «полностью замкнутый контур». Для Элары это требование КИИ, а не просто плюс.
- Финал: «становится лучше и проверяет аналитиков» — цифра покрытия и рост качества.
- Финальный ход: жюри выбирает эпик из галереи (3–5 готовых) или вводит свой, прогон вживую.
- Конкуренты: Atlassian Rovo, GitHub Copilot, Azure Boards + MCP, ClickUp Brain, Linear AI,
  StoriesOnBoard, приложения из Jira Marketplace; open-source — EpicToSprintPlanner,
  LLM-Jira-Automation. Все они облачные и не дают связки «локальная модель + контракты/код +
  прослеживаемость + цикл улучшения». Не заявляем «первые в мире».
- Отдельно OpenSpec: он организует разработку по спецификациям (proposal → specs → design →
  tasks → apply), а мы проверяем полноту и обоснованность бэклога интеграции. Его процесс
  не повторяем; наш результат может быть входом для него, для Jira и других систем.

### Закрытые вопросы (ответы команды, 13.11)
Общая рамка: **это демонстрация идеи, а не готовый продукт**. Ограничений, кроме времени, нет.
Где команда ответила «как лучше», решение принято нами.
- **Модель:** без разницы. На демо — Qwen3.8-27B (совпадает со схемой), подключение любой модели по API.
- **Метка:** label `<EpicSlug>_Autogenerate`, пробелы в имени эпика заменяем на `_`.
- **Иерархия Jira:** технические задачи — **Sub-task внутри истории**. Это родная иерархия
  Jira: задачи видны прямо в карточке истории, связь ставится одним полем `parent`.
  Связи-зависимости между задачами («блокирует») не делаем.
- **Трекер:** Jira Cloud Free, это презентация продукта.
- **Bitbucket (сценарий демо):** в репозитории `epics/`, `docs/`, `contracts/`. Push нового файла
  в `epics/` → вебхук → агент забирает файлы этого коммита через API Bitbucket → в UI
  сама запускается живая сборка → результат в Jira. Вопросы аналитика при запуске по вебхуку
  пропускаются (агент работает по допущениям и записывает их).
- **Контракты и код:** входы двумя путями — загрузка в UI или репозиторий. В репозитории агент
  находит `.proto` и OpenAPI-файлы (контракты и примеры) и по расширениям файлов и манифестам
  определяет язык. Код глубоко не анализируем: репозиторий — источник контрактов и стека.
- **Условия «промпт меняется» и «LLM через прослойку»** — для всех кейсов (подтверждено).
- **Эпики на защите:** галерея из 3–5 подготовленных эпиков на выбор жюри + поле
  «введите свой эпик».
- **Стек и репозиторий:** без разницы. Берём небольшой открытый репозиторий с gRPC-контрактами,
  кандидат — `GoogleCloudPlatform/microservices-demo` (Online Boutique: несколько сервисов
  на разных языках, контракты в `.proto`). Демо-эпик — интеграция этого магазина
  с внешней системой (например, службой доставки или платёжным провайдером), для которой
  мы готовим документацию и контракт.
- **Итоговый перечень задач:** для каждого демо-эпика сами готовим эталонную разбивку
  «как у команды после доработки». На защите загружаем её и показываем сравнение.

## 4. Варианты 3D-метафоры (выбор отложен)

## 5. Догадки и допущения (не проверены)
- Жюри ценит отсылки к своему миру (C++/Qt, gRPC, КИИ, ГОСТ, ОТК) больше абстрактной красоты.
- Ноутбук HONOR — это MagicBook Pro 2025: Intel Core Ultra 9 285H, Intel Arc 140T, 32 ГБ RAM,
  без NVIDIA. Характеристики взяты из ответа GPT, не проверены. ОС — **Linux** (подтверждено).
- Bonsai 2 9B на HONOR даст единицы или низкие десятки токенов в секунду (Vulkan может ускорить).
  Для разработки хватит, для живого демо — вряд ли. Нужно замерить через `llama-bench`.
- Слабый Bonsai справится с выделением требований и историями. Проверки кодом ловят
  его выдуманные API, но поиск противоречий может требовать Qwen3.8-27B.
- `Qwen3.8-27B-FP8` поместится на 48 ГБ с контекстом 32k. Нужно проверить на арендованной карте.
- Structured output в форке PrismML llama.cpp работает с нашей JSON-схемой. Нужно проверить.
- Jira Cloud и Bitbucket Cloud доступны из России без VPN. Официально не подтверждено,
  проверить регистрацией из сети площадки.
- LLM-судья на Qwen3.8-27B достаточно надёжно сопоставляет перефразированные задачи.
  На Bonsai может не справиться.

## 8. Итоги сверки с GPT
**Взяли:**
- слой требований `REQ-xxx`;
- покрытие, которое считает код по связям;
- проверки кодом до критиков-LLM, включая существование ссылок;
- поиск пробелов и противоречий (уровень 2);
- повторную проверку после ручных правок;
- принцип «документы — данные»;
- публикацию в Jira без дублей;
- OpenSpec в список конкурентов;
- отказ от PDF;
- одну модель на все шаги.

**Не взяли:**
- план на 3–4 человека (нас двое);
- Ollama (не поддерживает формат Bonsai);
