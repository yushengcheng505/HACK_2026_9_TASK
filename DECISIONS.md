## 2. Принятые решения

### Модель и инфраструктура
- **Модель подключается по API**: любой OpenAI-совместимый endpoint (llama-server, vLLM,
  при желании облачный API для сравнения). Провайдер, адрес и модель — в конфиге, код не меняется.
- Локальная модель работает **на ноутбуке HONOR** (на нём же разработка и демо):
  `prism-ml/Ternary-Bonsai-2-9B` через `llama-server` (форк llama.cpp от PrismML; Ollama не подходит).
  - Ноутбук: HONOR MagicBook Pro (FMB-P), Intel Core Ultra 9 285H (16 ядер), Intel Arc 140T
    (встроенная, драйвер Mesa), 30 ГБ RAM, **NixOS**. Видеокарты AMD нет — прежнее упоминание
    «NixOS + AMD R7» как отдельной машины было ошибкой: это тот же ноутбук.
  - Бэкенд — **Vulkan**, все слои на видеокарте. Он быстрее CPU при любом числе потоков
    (замеры и параметры — в подразделе «Локальная модель: замеры и настройки» ниже).
  - Модель и бинарники лежат в `~/Bonsai-demo` (официальный Bonsai-demo, релиз форка
    `prism-b10828-a153697`). Сервер запускается как пользовательский сервис systemd
    `bonsai-llm` из конфигурации NixOS (`~/nixos/modules/local-llm.nix`), адрес
    `http://127.0.0.1:8080/v1`.
- Демо: аренда GPU на clore.ai, **vLLM + `Qwen/Qwen3.8-27B-FP8`** на карте с 48 ГБ
  (L40S или A6000, примерно $0.4–0.5/ч).
  Запасной вариант: llama.cpp + GGUF Q4_K_M на RTX 4090/5090.
- Провайдеров и моделей может быть несколько: встроенный из `backend/.env` плюс добавленные
  в пульте (раздел «Модели», хранятся в `data/app.db`). Провайдер, модель и число параллельных
  запросов выбираются при запуске и записываются в прогон; параллельность меняется на лету.
- HAProxy есть на схеме, поэтому используем его по-настоящему (**пока не сделано**: в репозитории
  нет ни конфига HAProxy, ни `docker compose`):
  - основной сервер — vLLM на clore;
  - резервный — `llama-server` с Bonsai на ноутбуке.
- Режим thinking:
  - на шаге планирования — на минимуме, поток рассуждений показываем в UI;
  - на шагах генерации JSON — выключен.
  - Сделано частично: если модель присылает рассуждения (`reasoning_content`), они идут в поток
    и видны в пульте. Отдельного включения рассуждений на шаге планирования в коде нет —
    режим задаётся сервером модели или через `LLM_EXTRA_BODY`.
- Развёртывание (**пока не сделано**): `docker compose up` на ноутбуке (backend, frontend, HAProxy). Резервный
  `llama-server` в compose не входит: он работает на хосте как сервис `bonsai-llm`
  (ему нужен Vulkan и бинарники PrismML), HAProxy ходит к нему на `127.0.0.1:8080`
  (из контейнера — через `host.docker.internal` или `network_mode: host`).
  vLLM — на clore.ai. Вебхук Bitbucket доходит через туннель cloudflared.
- Интернет на площадке может подвести, поэтому есть режим проигрывания записанного прогона.

### Локальная модель: замеры и настройки
Замеры 13–14.11 на ноутбуке, **от батареи** (от сети может быть быстрее — не проверено).
Скорость — токены в секунду: «промпт» — чтение запроса, «генерация» — ответ.

| Вариант | Промпт | Генерация |
|---|---|---|
| CPU, 3 / 6 / 14 потоков (`llama-bench`) | 17,6 / 45,6 / 44,5 | 9,7 / 15,6 / 12,6 |
| Vulkan, все слои (`llama-bench`) | 76,5 | 24,6 |
| Шаг JSON через API, обычная модель | 67,8 | 17,8 |
| Шаг JSON через API, **MTP** | 56,8 | **22,4** |
| Рассуждения через API, обычная / MTP | 69,1 / 58,1 | 17,3 / 17,8 |

Шаг JSON — промпт ~1000 токенов, ответ ~280 токенов по строгой схеме; занимает ~40 с.

Что из этого следует:
- **Модель с MTP** (`Ternary-Bonsai-2-9B-PQ2_0-MTP-Q8_0.gguf`, встроенное предсказание
  следующих токенов): `--spec-type draft-mtp --spec-draft-n-max 2`. На JSON принимается
  ~95% предсказаний, генерация быстрее на четверть; на рассуждениях — вничью. Промпт читается
  немного медленнее, но при `-np 1` общий префикс промпта берётся из кэша.
- **Строго один слот, `-np 1`.** Два одновременных запроса при `-np 2` падают до ~1,4 токена/с
  на каждый. Бэкенд шлёт запросы к локальной модели по одному (очередь).
- **Порядок сэмплеров:** `top_k` до штрафов (`--samplers "top_k;penalties;top_p;min_p;temperature"`).
  С порядком по умолчанию `presence_penalty` роняет генерацию с ~18 до ~10 токенов/с.
- Контекст 32k против 16k и flash attention на скорость не влияют; ставим `-c 32768 -fa on`.
- `response_format: json_schema` (strict, `pattern`, `enum`) в форке PrismML работает,
  JSON валидный. Vision-проектор (`mmproj`) не загружаем — проекту он не нужен.
- Через API генерация ниже, чем в `llama-bench` (~18 против ~25), причина не найдена.
- Бинарникам PrismML нужна `libvulkan.so.1`. В systemd-сервисе её нет среди библиотек nix-ld,
  и без неё llama-server **молча считает на CPU** (чтение промпта ~15 токенов/с вместо ~60–85).
  Поэтому модуль передаёт сервису `vulkan-loader` и запускает с `--device Vulkan0`: без
  видеокарты сервис падает с ошибкой, а не тормозит. Проверка: `llama-server --list-devices`.
- **Полный прогон бэкенда на демо-эпике (14.11, от сети, видеокарта, настройки по умолчанию):**
  **1 ч 47 мин**, 28 вызовов модели. Чтение промптов 47 мин (166 тыс. токенов, ~59 т/с),
  генерация 58 мин (58 тыс. токенов, ~17 т/с). Итог: 20 требований, 5 пробелов, 0 вопросов,
  8 историй, 51 задача, покрытие 75%, выгрузка DOCX/XLSX/JSON открывается.
  - Один вызов зациклился и дописал до лимита 8192 токена (~8 минут впустую): в схемах
    нет ограничений на длину списков.
  - Два круга критика заняли половину времени и не улучшили результат: задач 65 → 51,
    ошибок проверок 14 → 7, но покрытие 85% → 75%. Поэтому один критик потом заменён командой
    проверяющих (раздел «Граф агента», п. 8).
  - Для живого демо Bonsai слишком медленный: демо — на арендованном GPU, Bonsai — резерв
    и разработка (`CRITIC_ROUNDS` 0–1, меньше `CONTEXT_CHAR_BUDGET`).

Профили запросов (сервер по умолчанию стоит на первом):
- **Генерация JSON, без рассуждений:** `temperature 0.7, top_p 0.8, top_k 20, min_p 0,
  presence_penalty 1.5`, `chat_template_kwargs: {"enable_thinking": false}`.
- **Планирование с рассуждениями:** в запросе `chat_template_kwargs: {"enable_thinking": true}`,
  `reasoning_effort` (по решению выше — минимальный, `"low"`; замер выше сделан на `"medium"`),
  `temperature 1.0, top_p 0.95, presence_penalty 1.0`.
  Рассуждения приходят отдельным полем `reasoning_content`.

Управление: `systemctl --user start|stop|status bonsai-llm`, логи — `journalctl --user -u bonsai-llm`.
Автозапуска нет, чтобы модель не держала видеопамять и батарею без надобности.

### Бэкенд — всё на Python
- Python 3.12 (uv), FastAPI, **LangGraph внутри процесса**, `SqliteSaver` (состояние графа,
  паузы на вопросы), SQLite (запуски, результаты, версии промптов).
- События на фронт идут по SSE, формат событий наш.
- Тот же модуль графа открывается через `langgraph dev` в LangGraph Studio. Это инструмент
  разработчика, а не часть демо. Studio нужны интернет и аккаунт LangSmith, но трассировка
  в LangSmith **выключена**, потому что данные не должны уходить наружу.
- Прослойка LLM: только OpenAI-совместимый API. Адрес и модель задаются в конфиге.
  Каждый ответ проверяется через Pydantic. При невалидном ответе — повтор с текстом ошибки.
  Где сервер умеет, используем `response_format: json_schema`.
- Промпты лежат в файлах `prompts/*.md` в git. Версии промптов хранятся в SQLite.
  Правки из пульта (раздел «Промпты») лежат отдельно, в `data/prompt_overrides/`, и действуют
  на следующие прогоны; сброс удаляет правку, исходник не меняется.
- Документы: `python-docx`. Таблицы: `openpyxl`.
- Прогон можно поставить на паузу и продолжить с последней контрольной точки графа.
- Запуск бэкенда с `--reload` перезапускает его при каждой правке файлов, и идущий прогон
  падает с ошибкой «Сервер перезапущен во время выполнения». Для демо и долгих прогонов
  запускать без `--reload`.
- Подробности и команды — в `backend/README.md`.

### Граф агента
Генерация разбита на маленькие шаги, по одному узлу графа на шаг. Принцип: **LLM отвечает
за смысл, всё детерминированное делает код** (разбор контрактов, проверки, покрытие, выгрузка).
Загруженные документы — данные, а не инструкции: их текст не меняет правила генерации.

1. **Разбор входов (код).** OpenAPI → список операций, `.proto` → сервисы, RPC, сообщения,
   документы (md/txt/docx, **без PDF**) → разделы. У каждого фрагмента ID (`DOC-3`,
   `API:POST /orders`, `PROTO:Telemetry.GetSnapshot`). Если фрагментов слишком много,
   отбираем их через BM25. Векторной базы нет.
2. **Определение целевого языка программирования:**
   - эвристика кодом: расширения файлов, опции в `.proto`, подсказки в OpenAPI;
   - при низкой уверенности — вопрос пользователю вместе с вопросами аналитика.
   - Подтверждения моделью, которое планировали между этими шагами, в коде нет.
3. **Выделение требований (LLM).** Атомарные требования `REQ-001…`: функциональные,
   интеграционные, нефункциональные. У каждого ссылки на источники.
4. **Аналитик (LLM).** Ищет неясности и задаёт 3–5 вопросов с 2–3 вариантами ответа и полем
   «свой ответ». Граф встаёт на паузу.
   - «Пропустить» — агент принимает допущения и явно записывает их.
   - Запуск по вебхуку — идём сразу по допущениям.
   - **Уровень 2, «по возможности»:** здесь же поиск пробелов и противоречий между эпиком,
     документацией и контрактом. Пример: эпик требует повтора платежа, а контракт не описывает
     идемпотентность → пробел, риск, вопрос к техлиду. В 3D это красный узел с лучами
     к двум источникам. В демо-контенте заранее закладываем 1–2 противоречия.
5. **Истории (LLM)**, каждая ссылается на `REQ-xxx`.
6. **Задачи (LLM)** отдельно для каждой истории. Каждая ссылается на `REQ-xxx` и фрагменты
   контракта. Включая задачи на интеграционное тестирование с тест-сценариями
   (уровень 2): метод, входные данные, ожидаемый результат, ошибки.
7. **Проверки кодом («ОТК»).**
   - Схема и обязательные поля, связи с родителями, дубли.
   - **Существование каждой ссылки**: ссылка на несуществующий RPC — выдуманный API, брак.
   - **Покрытие по связям**: требования без историй, задачи без обоснования, задействованные
     методы контракта без задач. Методы, которые не использует ни одно требование, —
     отдельный список «не задействовано — подтвердите» (это не ошибка).
8. **Проверка по смыслу — команда проверяющих (LLM)**, не больше 2 кругов
   (`CRITIC_ROUNDS`). Сначала планировали одного критика на весь эпик, но он не видел
   содержания задач, захлёбывался на большом эпике и не перепроверял свои находки.
   Теперь в круге:
   - **рецензент** — по одному на каждую историю: критерии приёмки, принятые решения, контракт;
   - **редактор стыков** — один на эпик: дубли и дыры между историями;
   - **упрощатель** — один на эпик: лишняя и переусложнённая работа;
   - **фильтр кодом**: находка без дословной цитаты из источников отсеивается, задачу,
     которая единственная закрывает требование, удалить нельзя;
   - **скептик** — пытается опровергнуть важные находки и пробелы аналитика;
   - подтверждённые находки уходят генератору задач на доработку, следующий круг проверяет
     только изменения.

   Журнал находок с вердиктами — поле `findings` результата и лист «Проверка» в XLSX.
   Старый критик остаётся для сравнения: `REVIEW_MODE=critic`. Дизайн —
   `docs/superpowers/specs/2026-11-14-review-workflow-design.md`. Замеры на мини-бенчмарке
   (`docs/review-benchmark.md`): старый критик находил 43% внедрённых дефектов, команда —
   93–100%; исправленных дефектов стало 93–100% вместо 71%.
9. **Выгрузка** DOCX / XLSX / JSON, включая статистику (п. 9).
10. **Jira** (**пока не сделано**, в коде нет): REST API v3 (описание в формате ADF), Epic → Story → **Sub-task**
    (Task в Jira нельзя сделать дочерним к Story). Метка `<EpicSlug>_Autogenerate`.
    - Из UI: просмотр → кнопка «Опубликовать». По вебхуку: автоматически, как в задании.
    - Сохраняем ID созданных задач: повторная публикация обновляет, а не дублирует.
    - Трекер подключается через адаптер.

После ручных правок в UI запускаются только проверки кодом (п. 7), без новой генерации.
Сделано: правка таблицы в пульте → `PUT /api/runs/<id>/result` → проверки и покрытие пересчитываются.

Одна модель на все шаги, разные промпты. Модель выбирается при запуске (провайдеры — выше).

### Фронтенд
Код — в `frontend/`, как запускать и устройство папок — в `frontend/README.md`.
- **Стек:** React 19 + TypeScript + Vite 8 + Tailwind CSS 4, линтер oxlint. Сцена нарисована
  на SVG + CSS-анимациях; three.js не подключён (3D-метафора отложена, раздел 4).
- **Архитектура** по слоям, импорты только «вниз»: `app → pages → widgets → features → entities → shared`.
  Каждый срез отдаёт наружу только свой `index.ts`.
- **Три точки входа:**
  - `/` — лендинг, к бэкенду не обращается;
  - `/agents/` — витрина роботов: 8 агентов в трёх состояниях (ожидание, работа, успех);
  - `/console/` — пульт декомпозиции, работает с бэкендом.
- **Агенты — 8 ролей в двух командах**, у каждого свой маленький робот (`entities/agent`):
  - декомпозиция: составитель требований, аналитик (пробелы и противоречия), автор историй,
    генератор задач;
  - проверка: рецензент, редактор стыков, упрощатель, скептик.

  Одни и те же модели роботов используются на лендинге, на витрине и в пульте.
- **Лендинг, сверху вниз:**
  - шапка с логотипом SYNAPS и одной кнопкой «Открыть консоль»;
  - заголовок «Одна задача. Команда маленьких AI-помощников» и короткое описание продукта;
  - сцена: ядро NAPS печатает и рассылает бумажные самолётики двум рядам агентов —
    сначала команде декомпозиции, потом команде проверки; над сценой этапы
    «Анализ → Декомпозиция → Проверка → Сборка», рядом консоль NAPS с логом;
  - строка задачи на сцене не интерактивная, кнопка «Попробуй сам» ведёт в пульт.

  Прогон на лендинге — анимация: состояние считает чистая функция `computeRunFrame(t)`
  (`features/team-run`), поэтому любой кадр воспроизводим; `?t=8.5` останавливает его на 8,5 с.
- **Пульт (`/console/`)**, боковое меню:
  - **Новый запуск** — форма эпика с файлами по четырём ролям, шаблоны эпиков, выбор провайдера,
    модели и числа параллельных запросов, режим «без вопросов»;
  - **Запуски** — журнал, обновляется сам;
  - **Модели** — провайдеры OpenAI-совместимых API;
  - **Промпты** — правка системного промпта каждой роли и сброс к исходнику;
  - **Бенчмарк** — отчёты мини-бенчмарка проверяющих.
- **Экран прогона** — живой поток событий по SSE, два режима:
  - «Агенты» — граф агентов с инспектором: что каждый получил, думал и выдал;
  - «Пульт» — ход прогона, трассировочная карта «источники → требования → история → задачи»,
    правка результата, ОТК, пробелы, вопросы аналитика на паузе.

  В шапке: пауза и продолжение, параллельность, выгрузка DOCX / XLSX / JSON,
  проигрывание записанного прогона с ускорением 4× / 10× / 25×.
  Контракт событий — `docs/superpowers/specs/2026-11-14-console-design.md`.
- **Дизайн** — тёмная тема с зелёным акцентом, общий для лендинга и пульта:
  - фон `#020E0E`, панели `#031412` / `#041A17`, бренд-зелёный `#01DE82`, мятный `#9DF7CF`,
    текст `#E6FFF3`; токены — в `frontend/src/app/styles/index.css`;

### Питч
- Главная фраза: **«Не генератор задач, а проверка полноты интеграции: каждая задача обоснована
  источником, каждый пробел найден до того, как его найдёт заказчик»**. Название продукта — SYNAPS.
- Главное: «понимает ваши контракты и код, каждая задача обоснована ссылкой на источник».
- Фундамент: «полностью замкнутый контур». Для Элары это требование КИИ, а не просто плюс.
- Финал: «становится лучше и проверяет аналитиков» — цифра покрытия и рост качества.
- Финальный ход: жюри выбирает эпик из галереи (3–5 готовых) или вводит свой, прогон вживую.
- Конкуренты: Atlassian Rovo, GitHub Copilot, Azure Boards + MCP, ClickUp Brain, Linear AI,
  StoriesOnBoard, приложения из Jira Marketplace; open-source — EpicToSprintPlanner,
  LLM-Jira-Automation. Все они облачные и не дают связки «локальная модель + контракты/код +
  прослеживаемость + цикл улучшения». Не заявляем «первые в мире».
- Отдельно OpenSpec: он организует разработку по спецификациям (proposal → specs → design →
  tasks → apply), а мы проверяем полноту и обоснованность бэклога интеграции. Его процесс
  не повторяем; наш результат может быть входом для него, для Jira и других систем.

### Закрытые вопросы (ответы команды, 13.11)
Общая рамка: **это демонстрация идеи, а не готовый продукт**. Ограничений, кроме времени, нет.
Где команда ответила «как лучше», решение принято нами.
- **Модель:** без разницы. На демо — Qwen3.8-27B (совпадает со схемой), подключение любой модели по API.
- **Метка:** label `<EpicSlug>_Autogenerate`, пробелы в имени эпика заменяем на `_`.
- **Иерархия Jira:** технические задачи — **Sub-task внутри истории**. Это родная иерархия
  Jira: задачи видны прямо в карточке истории, связь ставится одним полем `parent`.
  Связи-зависимости между задачами («блокирует») не делаем.
- **Трекер:** Jira Cloud Free, это презентация продукта.
- **Bitbucket (сценарий демо):** в репозитории `epics/`, `docs/`, `contracts/`. Push нового файла
  в `epics/` → вебхук → агент забирает файлы этого коммита через API Bitbucket → в UI
  сама запускается живая сборка → результат в Jira. Вопросы аналитика при запуске по вебхуку
  пропускаются (агент работает по допущениям и записывает их).
- **Контракты и код:** входы двумя путями — загрузка в UI или репозиторий. В репозитории агент
  находит `.proto` и OpenAPI-файлы (контракты и примеры) и по расширениям файлов и манифестам
  определяет язык. Код глубоко не анализируем: репозиторий — источник контрактов и стека.
- **Условия «промпт меняется» и «LLM через прослойку»** — для всех кейсов (подтверждено).
- **Эпики на защите:** галерея из 3–5 подготовленных эпиков на выбор жюри + поле
  «введите свой эпик».
- **Стек и репозиторий:** без разницы. Берём небольшой открытый репозиторий с gRPC-контрактами,
  кандидат — `GoogleCloudPlatform/microservices-demo` (Online Boutique: несколько сервисов
  на разных языках, контракты в `.proto`). Демо-эпик — интеграция этого магазина
  с внешней системой (например, службой доставки или платёжным провайдером), для которой
  мы готовим документацию и контракт.
- **Итоговый перечень задач:** для каждого демо-эпика сами готовим эталонную разбивку
  «как у команды после доработки». На защите загружаем её и показываем сравнение.

## 4. Варианты 3D-метафоры (выбор отложен)
1. **Созвездие с лучами к источникам**: эпик в центре, истории — планеты, задачи — спутники,
   по краю кольцо источников, клик по задаче — луч к источнику. Читается, реалистично по срокам.
   Риск — шаблонность.
2. **Живая схема с рисунка 1**: изометрический «завод» Bitbucket → агенты → HAProxy → vLLM,
   по которому текут токены. Сильно действует на организаторов, но саму декомпозицию
   хуже исследовать. Предел возможностей одного фронтендера.
3. **Сборочный чертёж**: эпик — изделие со штампом по ГОСТ, истории — сборочные единицы,
   задачи — детали в разнесённом виде, критики — ОТК со штампами «Принято»/«Брак».
   Самый уникальный, самый рискованный и дорогой.

**Рекомендация:** основа — вариант 1. Из варианта 3 берём штампы ОТК и штамп по ГОСТ (на экране
и в DOCX). Из варианта 2 — компактную живую схему в полосе конвейера, где видно переключение HAProxy.

**Что сделано вместо 3D:** идея варианта 1 реализована плоско, на SVG. В пульте есть трассировочная
карта: выбранная история показана цепочкой «источники → требования → история → задачи», клик
по элементу открывает обоснование и текст источника. Вкладка ОТК показывает проверки кодом.
Режим «Агенты» — граф реальных шагов прогона.

Ориентировочный бюджет времени:
- Лидер:

## 5. Догадки и допущения (не проверены)

- LLM-судья на Qwen3.8-27B достаточно надёжно сопоставляет перефразированные задачи.
  На Bonsai может не справиться.
