# Кейс «Агент-декомпозитор» (Элара, инженерный центр)

## Суть
Менеджер продукта пишет эпик текстом. Агент через локальную LLM разбивает его на
пользовательские истории (User Stories) и связанные с ними технические задачи,
выгружает результат в DOCX / XLSX / JSON и, если есть возможность, заводит всё в Jira.

## Слова представителя Элары (01_past.mp4, 38:00–45:00)

### Контекст заказчика
- Элара — импортозамещение в промышленности: печатные платы, контроллеры, SCADA, энергетика,
  радиоэлектроника (в т.ч. для поездов). Производство в Чебоксарах, инженерный центр в Москве.
- Работают на объектах **КИИ** (критической информационной инфраструктуры) [38:51], поэтому
  «промышленные» (облачные) нейросети использовать не могут. Только модели, развёрнутые
  **в своём замкнутом контуре**.
- Схема с рисунка 1 — их реальная инфраструктура; задачу решаем «по похожей схеме» [39:19].

### Остальные кейсы Элары (не наши, но важны для контекста)
Представитель описал три кейса подряд, каждый отделён фразой «Следующий слайд»:
- **Кейс 7 — модульные тесты** [39:39–40:59]. По контракту класса сгенерировать модульные тесты;
  можно дообучаться на существующих тестах проекта, проект любой. Оценивается: тесты выполняются,
  **ломаются при изменении кода** (то есть ловят мутации), адекватны и понятны.
- **Кейс 8 — интеграционные тесты** [40:59–42:33]. То же, но по внешним контрактам (gRPC или
  любой открытый API); можно опираться на существующие интеграционные тесты.
- **Кейс 9 — Агент-декомпозитор** [42:33–44:21] — наш.

Критерии оценки тестов из кейса 7 к нам **не относятся**.

### Условия про LLM и промпт [42:06–42:33]
Формально сказаны в конце кейса 8, перед переходом к нашему кейсу. По смыслу похожи на общие
для всех кейсов, но **это нужно подтвердить у представителя**. Мы выполняем их в любом случае:
- LLM любая, но **Qwen — «более интересно»**.
- Для демонстрации можно использовать и облачные нейросети, но при двух условиях:
  1. **промпт должен иметь возможность меняться**;
  2. **нейросеть подключается через прослойку**, чтобы её можно было заменить.

### Про наш кейс [42:33–44:21]
- Трекер не принципиален: «[неважно, про какой?] — это больше про сам подход» [43:01].
  Jira — пример, оценивают подход.
- Главный сценарий — **эпик на интеграцию с другой системой** [43:04]: взять документацию на эту
  систему, подгрузить её API (если есть) и разложить эпик на истории, а истории — на задачи.
- Связь с кейсом про интеграционные тесты: «написали интеграционные тесты… а как их
  запланировать?». То есть в декомпозиции должны быть и задачи на интеграционное тестирование.
- Зачем это нужно [43:42]: сейчас декомпозицию делают аналитики, и часто неудачно —
  **«интеграцию приходится доделывать»**. ИИ нужен **«для валидации этой работы и её ускорения»**.
  Значит, ценность двойная: (1) быстро сгенерировать декомпозицию; (2) проверить декомпозицию
  аналитика и найти, что пропущено.
- Дополнение, если основного функционала покажется мало [44:03]: проанализировать
  **приложение-конкурент** и его эпики, понять, чего не хватает нашему продукту, и какие
  задачи для этого нужны. Делать только после основной задачи.
- Задачи «абсолютно несложные» [44:21]. Значит, базовую функциональность сделают все,
  и выигрывает качество и подача. Финальная фраза: «будем надеяться, что студенты
  в конце удивят нас своими решениями».
- Представитель готов отвечать на вопросы. Наши вопросы задаём ему напрямую.

### Что это меняет в нашем решении
- Главный тезис питча — **работает полностью в замкнутом контуре**: ни одного внешнего вызова,
  трассировка LangSmith выключена, модель своя. Это прямое требование КИИ, а не просто «плюс».
- Слой работы с LLM: OpenAI-совместимый API, провайдер и модель меняются в конфиге или в UI
  без изменения кода (vLLM, llama.cpp, при желании облачный API).
- Промпты — в файлах, их можно редактировать в UI.
- Трекер — через адаптер: Jira как основная реализация, на защите упомянуть, что по тому же
  интерфейсу подключаются Jira DC и отечественные трекеры.
- Демо-эпики — **интеграционные**: внешняя система с документацией и `.proto`/OpenAPI.
- **Покрытие контракта** — ключевая метрика: каждый метод и сообщение API должен быть покрыт
  задачами (реализация + интеграционный тест). Это прямой ответ на «интеграцию приходится
  доделывать».
- Лаборатория получает второе, главное назначение — **валидация декомпозиции аналитика**:
  загружаем список аналитика → агент сравнивает со своим и с контрактом → показывает
  пропущенное и спорное.
- Анализ конкурента — опциональное дополнение в самом конце.
- Три кейса Элары образуют цепочку: **спланировать (9) → модульные тесты (7) → интеграционные
  тесты (8)**. Наш кейс — начало цепочки. Идея (не утверждена): в задачах на интеграционное
  тестирование агент выписывает тест-сценарии по контракту (метод, входные данные, ожидаемый
  результат, ошибки). Код тестов **не генерируем** — это чужой кейс, но наш результат можно
  передать на вход решениям кейсов 7/8.

## Принцип оценки и приоритеты
Оценивают **готовую, законченную реализацию**: важно качество решения поставленной задачи,
а не количество фич. Отсюда правило: **каждая фича либо доведена до конца, либо её нет**.
Недоделанная фича на защите хуже отсутствующей.

**Уровень 1 — ядро, должно работать безупречно на любом эпике (в т.ч. на эпике жюри):**
- Сценарий 1–7: эпик + необязательные входы (документация продукта, документация смежной
  системы, `.proto`/OpenAPI, примеры контрактов; форматы md/txt/docx, **без PDF**) →
  LLM через прослойку → аккуратно оформленные DOCX / XLSX / JSON.
- Качество самой декомпозиции:
  - **слой требований**: эпик → атомарные требования `REQ-xxx` → истории → задачи,
    у каждого элемента ссылки на требования и источники;
  - истории в формате «Как… я хочу… чтобы…» с критериями приёмки;
  - типизированные технические задачи (включая интеграционное тестирование);
  - **покрытие считает код по связям**: непокрытые требования, задачи без обоснования,
    методы контракта, которые задействованы требованиями, но не покрыты; отдельно список
    «не задействовано в эпике — подтвердите»;
  - **проверки кодом**: схема, связи, дубли, существование каждой ссылки на источник
    (ловит выдуманные API);
  - критики-LLM только по смыслу (не больше 2 кругов);
  - уточняющие вопросы с вариантами ответов.
- Jira: Epic → Story → Sub-task, label `<Epic>_Autogenerate` (п. 8); статистика в JSON (п. 9).
  Из UI — просмотр и кнопка «Опубликовать», по вебхуку — автоматически. Повторная публикация
  обновляет, а не дублирует.
- Промпты в файлах; модель подключается по API: любой OpenAI-совместимый endpoint, меняется
  в конфиге. Загруженные документы — данные, а не инструкции для модели.
- Надёжность: строгий JSON по схеме, повтор при ошибке, режим проигрывания записанного прогона.
- Фронт: основная 3D-сцена (живая сборка + клик по задаче показывает источник) + табличный вид.

**Уровень 2 — бонусы со слайда, маленькие, но законченные:**
- определение языка программирования;
- история запусков;
- сравнение с итоговым списком задач + рекомендации (валидация работы аналитика);
- вебхук Bitbucket (он есть на схеме);
- визуализация покрытия в 3D;
- тест-сценарии в задачах на интеграционное тестирование;
- **поиск пробелов и противоречий** между эпиком, документацией и контрактом: вопросы
  к техлиду, в демо заранее заложено 1–2 противоречия («по возможности», не обязательно).

**Уровень 3 — только если уровни 1–2 уже отполированы:**
- демонстрация переключения HAProxy на резерв;
- анализ последствий: изменённый `.proto` в push → какие задачи затронуты (без фокуса);
- вопросы комментарием в Bitbucket и коммит файлов результата обратно в репозиторий;
- забор итогового списка задач из Jira;
- редактор промпта с перезапуском и графиком роста оценки;
- анимация «улетания» задач в Jira;
- анализ конкурента.

## Заданная инфраструктура (рисунок 1, «Общая схема»)
```
BitBucket -> WebHook -> Движок агентов (LangGraph / CrewAI) -> HAProxy -> vLLM Server (Qwen 3.8)
Разработчик (VS Code / MS VS / Qt) ------------------------------> HAProxy
```
Что из этого следует для нас:
- LLM — это vLLM, то есть OpenAI-совместимый API (`/v1/chat/completions`) за HAProxy.
  Адрес, модель и ключ задаём в конфиге, ничего не зашиваем в код.
- Движок агента — LangGraph или CrewAI. Это прямо указано на схеме, поэтому берём один из них
  (предлагаю LangGraph: граф шагов детерминированный, его легко отлаживать).
- Запуск должен работать через WebHook (например, от BitBucket). Кроме того нужен ручной
  запуск: CLI или простой UI.
- «Qwen 3.8» — семейство Qwen3.8 (`Qwen/Qwen3.8-27B`). На демо: vLLM + `Qwen3.8-27B-FP8`
  на clore.ai; локально: `Ternary-Bonsai-2-9B` через llama.cpp на ноутбуке HONOR (Linux). Слабая
  локальная модель требует маленьких шагов генерации. Чтобы JSON на выходе был стабильным,
  используем structured output (`response_format: json_schema`).

## Обязательный минимум (MVP) — пункты 1–7 сценария
1. **Ввод эпика** текстом (название и описание).
2. **Документация на продукт** — подгружается, если она есть (файлы: md/txt/docx).
3. **Документация на смежную систему** — подгружается, если эпик связан с интеграцией.
4. **API-контракт смежной системы** — подгружается, если он есть (OpenAPI/Swagger, gRPC `.proto` и т.п.).
5. **Примеры и реализованные контракты** взаимодействия в исходной системе — подгружаются, если они есть.
6. **Запрос к локальной LLM** (vLLM через HAProxy).
7. **Когда ответ получен**, агент по **промпту** формирует перечень историй и связанных с ними
   задач и выгружает его в трёх форматах:
   - `*.docx`
   - `*.xlsx`
   - `*.json`

Все входы из п. 2–5 необязательные: агент должен работать и на одном тексте эпика.

## Желательно (по сценарию)
8. *«При наличии технической возможности»* — создавать в **Jira** истории и задачи:
   - со связями (эпик -> история -> задача);
   - с меткой `<Имя Эпика>_Autogenerate` (в задании это названо «метрика»; решили, что это label).
9. **Статистика в JSON**: сколько историй и технических задач сгенерировано для эпика.

## Дополнительные пожелания (бонусы)
- Определять целевой язык программирования по документации или описанию API, а если не получается —
  спрашивать пользователя.
- Интеграция с Jira (то же, что п. 8).
- Хранить результаты генерации (история запусков).
- Сравнивать результат генерации с итоговым перечнем задач (эталоном, который составил человек)
  и давать рекомендации по отладке промпта или по формулировке запроса.
- Держать основной промпт в отдельном файле, чтобы его можно было настраивать и отлаживать;
  дополнительные промпты желательно вынести так же.
